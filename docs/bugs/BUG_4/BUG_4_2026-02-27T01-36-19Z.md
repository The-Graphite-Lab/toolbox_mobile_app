# BUG_4 Instance - 2026-02-27T01-36-19Z

## Description
- Ride-along sessions ended locally on iOS, but backend artifacts were missing: no persisted session rows, no turns, and recording upload URL failures.

## Symptoms Observed
- UI showed session lifecycle locally, but backend state was incomplete.
- Upload warning surfaced in UI (`Session ended, but recording upload failed...`).
- Session and turn records were not appearing in backend data.

## Troubleshooting Steps
1. Reviewed iOS plugin API request path and auth usage.
   - Result: Native calls only include `Authorization` when `apiAuthToken` is provided.
2. Reviewed `RideAlongsTab` session start call to native plugin.
   - Result: `apiAuthToken` was not being passed into `AudioRecording.startRideAlongSession`.
3. Reviewed stop/upload path in `RideAlongsTab`.
   - Result: Web upload fallback attempted on native file paths, causing misleading upload warnings.
4. Implemented fixes:
   - Fetch and pass `getApiAuthToken()` into native session start options.
   - Restrict JS upload fallback to web-style URLs (`blob:`, `data:`, `http(s):`) only.
   - Add native API response/error reporting in iOS plugin for non-2xx and transport failures.
5. Verified native iOS build.
   - Result: `xcodebuild` simulator build succeeded.

## Resolution Summary
- Root cause was missing auth token propagation into native iOS backend calls.
- Secondary issue was misleading upload fallback behavior running in native contexts.
- Applied auth propagation + better native error observability + safer web-only upload fallback.

## Lessons Learned
- Any native HTTP path that bypasses Amplify must receive an explicit auth token from JS.
- Mixed web/native upload flows should gate fallback logic by URL scheme/platform to avoid false diagnostics.
